Glossary

The Memory Management Unit (MMU)

Lesson 3 of the x86 Processor Modes series.

1. What the MMU Does

The MMU is a hardware unit inside the CPU that translates every address a program uses (virtual address) into the actual physical RAM location (physical address). This translation is invisible to user programs — they see a clean, flat 4 GB address space regardless of how memory is physically laid out.

Enabling the MMU (via CR0.PG bit) adds an indirection layer between the program and memory. Disabled: virtual address = physical address. Enabled: virtual address → page tables → physical address.

Key insight from Lesson 1 & 2: Real mode has no MMU. Protected mode can have one — CR0.PE and CR0.PG are independent bits. You can have protected mode without paging (pure segmentation), or protected mode with paging (what JCore uses).

2. Page Tables on 32-bit x86

On 32-bit x86 protected mode, the MMU translates addresses through two levels of tables:

Virtual address (32 bits):
┌──────────┬──────────┬────────────┐
│   PD idx │   PT idx │   offset   │
│  bits 31-22 │ bits 21-12 │ bits 11-0  │
│  10 bits │  10 bits │  12 bits   │
└──────────┴──────────┴────────────┘
               ↓               ↓         ↓
Page Dir  ─→  PDE  ─→  Page Table ─→  PTE  ─→  Physical page

Page Directory (1024 entries × 4 bytes = 4 KB): each entry points to a page table. Located at the physical address in CR3.

Page Table (1024 entries × 4 bytes = 4 KB): each entry points to a 4 KB page frame. 1024 × 4 KB = 4 MB per page table.

Total coverage: 1024 page dir entries × 4 MB each = 4 GB virtual address space.

3. Page Table Entry Bits

BitNameMeaning
0P (Present)Page is in physical memory. If 0, accessing this address triggers a page fault.
1R/W0 = read-only, 1 = read-write.
2U/S0 = supervisor (Ring 0–2), 1 = user (Ring 3).
3PWTPage-level write-through.
4PCDPage-level cache disable.
5A (Accessed)Set by CPU when page is read/written — used by page-replacement algorithms.
6D (Dirty)Set by CPU when page is written to — page must be saved to disk before eviction.
7PS (Page Size)In PDE: 0 = points to page table, 1 = 4 MB page (huge page).
8G (Global)Prevents TLB flush on CR3 reload (invpcid needed to evict).
9–11AvailAvailable for OS use (e.g., Linux's young/dirty tracking).
12–31Frame addressPhysical address of the page (4 KB aligned — lower 12 bits are zero).

4. The TLB: The MMU's Cache

Walking two levels of page tables on every memory access would be catastrophically slow. The Translation Lookaside Buffer (TLB) is a hardware cache inside the CPU that stores recent virtual→physical translations.

Typical TLB miss (on x86): hardware walks the page tables automatically (called a hardware page table walk) and loads the translation into the TLB. The OS is only involved if the page isn't present — that's a page fault (#PF, interrupt 14).

When the OS changes a page table entry, it must invalidate the corresponding TLB entry with invlpg (or reload CR3 to flush the entire TLB). Without this, the CPU might use a stale translation.

5. MMU in JCore

JCore relies on GRUB to set up initial paging. The Multiboot2 header in crt0.S requests a linear framebuffer, and GRUB prepares the environment with paging enabled, identity-mapping the kernel's physical memory to its virtual address.

JCore defines the CR0 paging flag:

// from src/Headers/misc.h
#define CR0_PG  0x80000000   /* enable paging */

When a program accesses an unmapped or protected page, the CPU raises interrupt 14. JCore's page fault handler is in src/Assembly/exception.S (line 138):

#define PAGE_FAULT_VECTOR $14
...
pushl PAGE_FAULT_VECTOR   ; push vector number and handle

The error code pushed with the page fault tells JCore what happened:

  • Bit 0 (P): 0 = non-present page, 1 = protection violation
  • Bit 1 (W/R): 0 = read, 1 = write
  • Bit 2 (U/S): 0 = supervisor, 1 = user

JCore's memory manager (the Memory/gc_* files) is a garbage collector that manages Java object heaps. It operates on top of the page-level abstraction provided by the kernel — it doesn't set up page tables itself, but relies on the underlying page mapping for isolation between domains.

6. MMU and the TCB

The MMU is part of the TCB (Lesson 2). It's the hardware mechanism that enforces process isolation — Domain A cannot access Domain B's memory because the page tables say so. If the MMU is defective or if the OS sets up page tables incorrectly, isolation fails.

The page tables themselves are a software data structure (in the TCB), but the MMU that interprets them is hardware. This is the "hardware-enforced security" that makes microkernel architectures viable — the MMU is the trusted third party that mediates every memory access.
