Tiny LLM on Baremetal ARM

Running a transformer on the BBAI without Linux

The Screening Question

Can you run an LLM on an RTOS? Yes — a small one. The model runs as a compiled function. No PyTorch, no Python, no OS services needed. Just matrix multiply and softmax.

The sweet spot for your BBAI (1 GB DDR, no swap): 15M–42M parameter models in INT8 or 1M–15M in FP32.

The Software Stack

Karpathy's llama2.c is the right reference: a single ~700-line C file that loads a weight file and runs the forward pass. No dependencies. No malloc in the hot path. It compiles with any C compiler including our clang ARM cross-compiler.

llama2.c architecture:
   main()
    ├── build_transformer()    — reads weights from .bin file
    ├── generate()             — autoregressive loop
    │    └── transformer()     — one forward pass
    │         ├── rmsnorm()    — 2× per layer
    │         ├── matmul()     — matrix multiply (attention + FFN)
    │         ├── attention()  — scaled dot-product
    │         ├── softmax()    — attention weights
    │         └── ffn()        — feed-forward network
    └── print token

Total: ~700 lines. No external libraries.

Two Ways to Load Weights

Your RTOS has no filesystem. Here are the options:

ApproachHow it worksComplexityMax model size
Link into kernel xxd -i model.bin > model_data.c → compile and link as a giant array Trivial ~100 MB (linker can handle it)
Load from SD card U-Boot's fatload mmc 0:1 0x90000000 model.bin, then pass address to kernel U-Boot side only (no driver needed) Up to ~900 MB (limited by DDR)
SD card driver in RTOS Write an MMC driver + FAT reader in your RTOS High (SD protocol, FAT parsing) Up to 900 MB

For a first run, use the link into kernel approach. It's the least code and the model is already in RAM at boot.

Minimal Port: What to Change

Taking llama2.c to your RTOS:

  1. Remove file I/O: Replace fopen/fread with a pointer to the linked weight array. The build_transformer() function becomes a single memcpy or just sets pointers.
  2. Remove stdout: Replace printf("%c", token) with your uart_putc().
  3. Remove malloc: llama2.c already allocates everything at startup. Change malloc() to static arrays or addresses in DDR.
  4. Adjust the memory layout: The transformer needs ~64–128 MB for activations, key-value cache, and the weight matrix. Update linker.ld to reserve this region.
// Before (llama2.c):
float *w = (float*)malloc(weight_size);
FILE *f = fopen("model.bin", "rb");
fread(w, 1, weight_size, f);

// After (your RTOS):
extern float _binary_model_bin_start[];
float *w = _binary_model_bin_start;
// No fopen, no fread

With a TinyStories-15M model linked into your kernel, boot and inference looks like:

Generation took 3.2 seconds (13.1 tokens/sec)

That's 42 tokens at 13 tok/s — about 75 ms per token, or 5–6 tokens per SysTick if your tick is 10 ms. The LLM becomes just another function your RTOS calls.

What This Teaches You

  • How transformer attention works at the C level (no framework hiding the math)
  • How to cross-compile a "Linux" program into a baremetal binary
  • How to layout a large static data array in DDR with the linker
  • How much compute a Cortex-A15 can actually deliver (don't trust specs — measure)

Quiz

Q1: Why can't you run a 7B-parameter model on the BBAI?

Answer: 7B × 4 bytes = 28 GB just for weights. The BBAI has 1 GB total DDR.

Q2: What stops you from using printf from llama2.c in your RTOS?

Answer: Nothing — you can provide your own putc-based printf, or replace printf calls with direct uart_puts. The linker resolves the symbol either way.

Q3: Where do the model weights live in memory at boot time with the "link into kernel" approach?

Answer: In the kernel binary, linked at a fixed address in DDR (e.g., 0x90000000). They're part of the ELF's .rodata or .data section. No loading needed — they're already there when U-Boot jumps to the kernel.
