RTOS vs General-Purpose OS

What makes an OS "realtime" and why you can't run Linux on a microcontroller

The One-Sentence Answer

A general-purpose OS optimizes for average-case throughput. An RTOS guarantees worst-case deadline satisfaction. Everything else — scheduler, memory model, IPC — follows from that.

If you ask Linux "how fast can you dispatch this thread?" it will tell you the average. If you ask an RTOS the same question, it will tell you the maximum — and that number will be reliable regardless of system load.

Why the Same Hardware Needs Different Software

The Cortex-A15 on the BBAI is powerful enough to run Linux. It's also powerful enough to run a tiny deterministic RTOS. The difference is not in the hardware — it's in what you ask the software to guarantee.

The Three Pillars of Realtime

1. Scheduling

An RTOS uses fixed-priority preemptive scheduling. Each task has a priority. The highest-priority ready-to-run task always runs. No aging, no fairness adjustment, no dynamic priority boosting. This makes the worst-case dispatch time predictable: it's the time to save the current context and restore the highest-priority task's context.

A GPOS uses fair-share scheduling (CFS on Linux). It tries to give every thread an equal share of CPU time. This is great for interactive workloads — your text editor doesn't starve because a compiler is running. But it makes latency unpredictable under load.

2. Kernel Preemption

In a standard GPOS, the kernel can disable preemption for long stretches (e.g., while walking a linked list of tasks). In an RTOS, every kernel operation is bounded — the longest critical section is measured in microseconds, not milliseconds. This is why Linux needs the PREEMPT_RT patch to approach realtime behavior: it breaks long critical sections into preemptible pieces.

The corollary: The RTOS kernel must be simpler than a GPOS kernel. Complex data structures (hash tables, red-black trees) have unpredictable traversal times. The RTOS uses arrays and linked lists because their operation counts are known and bounded.

3. Priority Inversion Protocol

This is the classic RTOS trap. Consider three tasks:

Task A (high priority) — needs mutex M
Task B (medium pri)   — pure CPU, no mutex
Task C (low priority) — holds mutex M

Without priority inheritance: C holds M, A blocks on M, B preempts C (B has higher priority than C). A is now blocked until B yields and then C finishes its critical section. The delay to A is unbounded — it depends on how long B runs. This is unbounded priority inversion.

With priority inheritance: When A blocks on M, C inherits A's priority temporarily. B can no longer preempt C. C finishes its critical section, releases M, and drops back to its original priority. A runs. The delay is bounded to C's critical section length.

A GPOS may or may not implement priority inheritance. Linux does (since 2.6.18 with futex), but only for realtime scheduling policies (SCHED_FIFO, SCHED_RR). The default (SCHED_OTHER) does not — because fairness is the goal, not deadline satisfaction.

Where This Leaves Your RTOS

Your RTOS on the BBAI is a trust-based, fixed-priority preemptive RTOS with domain isolation. It's not trying to be Linux. It's trying to be:

  • Deterministic — PendSV + fixed priorities, no aging
  • Simple — static allocation, bounded kernel operations
  • Transparent — you can trace every instruction of every context switch

This is exactly the right set of tradeoffs for a baremetal OS you're building to learn. Linux makes different tradeoffs because it serves different goals — fairness, isolation, and throughput across thousands of processes.

Quiz

Q1: A high-priority task misses its deadline because a medium-priority task is running. What mechanism is missing?

Answer: Priority inheritance on the mutex that the high-priority task is waiting for (or the low-priority task holding the mutex doesn't exist — in which case the scheduler itself is the problem).

Q2: Linux's CFS scheduler gives each of 100 tasks an equal share. An RTOS with the same 100 tasks runs task A (priority 5) then task B (priority 99). Why won't B ever run if A is compute-bound?

Answer: Fixed-priority preemptive scheduling — B has higher priority, so it runs immediately. But if A is higher priority than B, A runs and B never gets CPU. This is by design: the developer assigned priorities to meet deadlines.

Q3: Your RTOS kernel disables interrupts for 300 µs during the context switch. Is this acceptable?

Answer: It depends on your deadline requirements. 300 µs is very long for an RTOS (typical target is <10 µs). The interrupt-off time during PendSV should only cover saving/restoring registers — not the scheduler_next() call, which can run with interrupts enabled if a queue protects the ready list.
