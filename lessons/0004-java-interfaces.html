Lesson 4: Java Interfaces

From the interface keyword to invokeinterface bytecode.

Mission Connection: FlintJVM needs to resolve invokeinterface at runtime. Understanding how interfaces compile and link is essential to debugging why your Java program throws UnsupportedOperationException instead of running.

1. What Is an Interface?

An interface is a reference type that defines a contract: a set of method signatures (and since Java 8, default methods and static methods) that implementing classes must provide. Unlike a class, an interface cannot be instantiated directly — it only describes what a type can do, not how.

public interface Drawable {
    void draw();                      // abstract method
    default void print() {            // default method (Java 8+)
        System.out.println("printing");
    }
}

public class Circle implements Drawable {
    public void draw() {              // must implement draw()
        System.out.println("circle");
    }
    // print() inherited from the interface
}
FeatureClassInterface
Can be instantiatedYes (new)No
FieldsAnyOnly static final (constants)
MethodsConcrete + abstractAbstract + default + static
Multiple inheritanceNoYes (multiple interfaces)
Class file flagNone (0x0000)ACC_INTERFACE (0x0200)

2. How javac Compiles Interfaces

Interface declaration → .class file

A Java interface compiles to a .class file identical in structure to a class file, with one difference: the access_flags field has the ACC_INTERFACE bit (0x0200) set. The JVM spec says a class must have this bit set to be treated as an interface; otherwise, it's a class.

// Source: Drawable.java
public interface Drawable {
    void draw();
}

// Decompiled class file flags:
// access_flags = ACC_PUBLIC | ACC_INTERFACE | ACC_ABSTRACT
//                     0x0001 |       0x0200 |       0x0400  = 0x0601

Method call → invokeinterface bytecode

When you call a method through an interface reference:

Drawable d = new Circle();
d.draw();  // compiles to invokeinterface

This produces a single bytecode instruction:

InstructionOpcodeOperands
invokeinterface0xB9index (constant pool), count (args + 1), 0

The invokeinterface instruction looks up the method in the constant pool (a CONSTANT_InterfaceMethodref entry, tag 11), then performs a dynamic dispatch — walking the receiver's class hierarchy to find a concrete implementation.

3. Why invokeinterface Is Different

There are four JVM invoke instructions. Each has different dispatch semantics:

OpcodeInstructionReceiverDispatch
0xB7invokespecialKnown at compile timeDirect (no vtable)
0xB8invokestaticNone (static)Direct
0xB9invokeinterfaceInterface referenceInterface method table (itable)
0xB6invokevirtualClass referenceVirtual method table (vtable)

The challenge with invokeinterface: unlike invokevirtual (which uses a fixed offset into a vtable), the JVM must search the receiver's class for the interface method because interfaces can be implemented by unrelated classes. To optimize this, JVMs typically build interface method tables (Itables) — per-class lookup tables that map interface methods to concrete implementations.

Inside FlintJVM: The opcode OP_INVOKEINTERFACE (0xB9) is handled by the invokeInterface method in flint_execution.cpp:62. It reads a CONSTANT_InterfaceMethodref (tag 11 from the constant pool), resolves the method, and dispatches using the receiver's class loader. Look at flint_const_pool.h:17 for how interface method references are represented in memory.

4. Default Methods (Java 8+)

Java 8 introduced default methods — methods with a body defined directly in the interface. This changes the dispatch: if no implementing class provides an override, the JVM falls back to the interface's default implementation.

public interface Named {
    default String name() { return "unknown"; }
}

public class Person implements Named {
    // inherits name() -> returns "unknown"
}

public class Dog implements Named {
    public String name() { return "fido"; }  // overrides default
}

In the class file, default methods are marked with ACC_DEFAULT (a synthetic flag). The JVM stores them in the interface's method table and copies them into implementing classes' itables unless overridden.

5. Key Takeaways

  1. Interfaces are just classes with ACC_INTERFACE set. Same .class file format, same constant pool.
  2. Calling an interface method uses invokeinterface (0xB9), which requires itable dispatch — slower than vtable dispatch.
  3. FlintJVM handles all of this in flint_execution.cpp, flint_const_pool.cpp, and flint_class_loader.cpp — the embedded runtime classes from java.base.jar include standard library interfaces like Iterable, Comparable, Runnable, etc.
  4. Your HelloRPi test failed on UnsupportedOperationException — not because of interface dispatch, but because invokedynamic (for Java 11 string concat) isn't implemented in this FlintJVM build.

6. Practice: Trace the Dispatch

Given these types:

interface Talker { String talk(); }
abstract class Animal implements Talker {}
class Cat extends Animal { public String talk() { return "meow"; } }

Talker t = new Cat();
t.talk();
  1. What access flag will Talker's class file have?
  2. What bytecode instruction is t.talk() compiled to?
  3. When the JVM dispatches t.talk(), does it use a vtable or an itable?

Answers: (1) ACC_INTERFACE | ACC_ABSTRACT | ACC_PUBLIC = 0x0601, (2) invokeinterface (0xB9), (3) Itable (interface method table).
