Lesson 0003

The Blind Flight: Debugging on Real Hardware

QEMU is a forgiving angel. It emulates a clean x86-64 with a perfect serial port, a stable memory map, and no stray interrupts. Real hardware is a spiteful god: COM ports sometimes live at 0x3F8, sometimes at 0x2F8, sometimes not at all. Your kernel that prints a victory message under QEMU may produce only silence on metal.

This lesson teaches you how to fly blind -- how to debug when the screen is black, the serial cable is silent, and you have no idea whether the CPU even reached your start label.

1. Verify Your Bootloader Still Works

Before you even write a debug strategy, confirm your bootloader payload is reaching kernelMain on real hardware. A surprising percentage of "my kernel crashes on real hardware" is really "my bootloader fails to read the kernel image from the USB stick."

Your ISO image works because QEMU emulates a CD-ROM. A real machine boots from a USB flash drive or a real CD. The bootloader (GRUB, or your custom loader) must read the kernel sectors successfully. If your kernel is loaded at the wrong physical address, the long_mode_start jump lands in the BIOS or in random memory, and you get no output and no crash -- the CPU might just be executing garbage.

Golden Rule #1: Burn the ISO to a real CD, or use dd to write it to a USB stick. Boot it. If you get a black screen, literally just your bootloader stage failing, fix the bootloader first.

Your bootloader should have a way to emit a beep, flash the num-lock LED, or write a byte to a known I/O port before jumping to the kernel. If it does these three things and the kernel is silent, then you have a kernel-level bug. If it does none of them, you have a boot-media bug.

2. The Serial Port Is Your Lifeline

You already have a printf that sends characters out of COM1 (0x3F8) to serial in QEMU. That same COM port exists on almost every x86-64 motherboard, but there are three fatal differences on real hardware:

  1. Port Address: The BIOS may have relocated the serial port. Check 0x40:0x00 in the BDA (BIOS Data Area), or just try 0x2F8 (COM2), or use the newer MMIO-based serial (e.g., on some Intel NUCs).
  2. Line Settings: QEMU defaults to 115200 baud, 8N1, no flow control. Real hardware might be left at 9600 baud by the BIOS. You must explicitly program the baud rate via the Divisor Latch.
  3. Transmitter Holding Register: On QEMU, you can spam bytes to port 0x3F8 immediately. On real hardware, you must wait for the THR (Transmit Holding Register) to be empty (bit 5 of LSR, or bit 5 of the 16550 status register at offset 5). Polling too fast or writing when not ready will drop characters or hang the CPU.
Your current kernel.cpp does:
while(!(Read8(0x3F8 + 5) & 0x20)); Write8(0xStress, str[i])
That is almost correct, but if Read8 and Write8 don't in-line or if the compiler re-orders the IO, you will lose data. Use volatile for every port IO in C++ to defeat the optimizer. Also set the baud rate explicitly: the BIOS might have left the port in 9600 baud or a weird state.

Connection: You need a USB-to-TTL serial adapter (e.g., FT232, CP2102, CH340). Connect GND to pin 5, TX to pin 3 (RX on the host), and RX to pin 2 (TX on the host). Open a terminal with screen /dev/ttyUSB0 115200 or minicom -D /dev/ttyUSB0 -b 115200.

3. When the Screen Is Black: The In-Situ Blinkenlight

What if your kernel crashes before it even reaches printf? Maybe the GDT or paging setup is wrong, and the CPU triple-faults immediately. You need a way to leave breadcrumbs.

The most reliable early-boot debug signal is the POST Code: writing a single byte to port 0x80. Many motherboards (especially server-grade and some enthusiast boards) have a POST code LED that displays the last byte written. Even if they don't, a PCIe POST card can be bought for a few dollars and does the same.

This is absurdly useful because it requires zero working memory, zero initialized data, and no driver stack. If 0x10 shows up on the POST LED, your bootloader and transition to long mode works. If 0x20 does not show up, you know the crash is inside setup_paging(). Binary search your way down.

4. Black Screen of Death: The Systematic Approach

When you get a black screen and no serial output, do not guess. Follow this checklist in order.

  1. Check your boot media. Is the ISO actually bootable on real hardware? Does the bootloader have a fallback path if the disk geometry is different? (e.g., does it read a hardcoded LBA that is off by one on real hardware?)
  2. Verify the bootloader runs. Add a heartbeat(0x01) immediately after the BIOS hands over control. If you don't see it, your boot media is corrupted or unsupported.
  3. Verify long mode entry. Add heartbeat(0x10) at the top of your 64-bit entry point. If you see it, you are in long mode. If not, your GDT or paging setup is wrong (check PAE, PGE, and LM bits in CR4/CR0/EFER).
  4. Check video mode. Are you sure your kernel even tries to write to VGA text mode? If it blindly assumes 0xB8000 is a valid physical address for a framebuffer, and you're running on a system with UEFI GOP, there might be no VGA text mode at all. Use serial, not video, for initial debug.
  5. Serial silence: If uart_init() runs but nothing appears, check: is the baud rate correct? Is the port at the right IO address? (Try 0x2F8 for COM2). Is the FIFO enabled with a small threshold? Does the host-side terminal program match the settings?
  6. Triple fault / hang: If your kernel sets up an IDT and enables interrupts (sti) before all ISRs are good, a single APIC timer tick will triple-fault and reboot. Ensure your APIC timer handler is installed before enabling interrupts, or just leave cli until the kernel is fully initialized.

5. The GDB Stub: Interactive Debugging Over Serial

Once you have a serial port, the ultimate debugging tool is a remote GDB stub baked into your kernel. Instead of guessing, you set a breakpoint from GDB, step through C++ code, and inspect registers and memory.

A minimal GDB stub for x86-64 handles the g (read registers), m (read memory), M (write memory), and c (continue) packets. It lives in your interrupt handler (or a dedicated handler for the debug exception, #DB, vector 1) and communicates over the same serial port.

This is too large to fully inline here, but the key concept is: in your kernel.cpp, before the main loop, call gdb_init(). This installs the #DB handler (for hardware breakpoints via DR0-DR3) and the int3 handler (for software breakpoints). When a gdb_interrupt_handler runs, it sends a stop packet, then waits for packets like s (step) or c (continue owning).

The primary source for this is the OSDev Wiki: Debugging with GDB and the kgdb implementation in Linux.

6. The Real Hardware Checklist

Before ever booting on real metal, you should verify the following programmatically:

  • Does the Multiboot2 / Multiboot1 info structure have a valid memory map? (Real hardware memory maps are not the flat 1:1 identity map of QEMU).
  • Are you reading APCI tables (RSDT/XSDT)? You cannot rely on the BIOS reserving memory for you; the EBDA (Extended BIOS Data Area) might be at a different location.
  • Interrupts: do you map the APIC before assuming PIC is off? Some hardware leaves the PIC in a state that conflicts with the APIC. In QEMU, this rarely breaks; on metal, it does.
  • DMA / ATA: Your ATA driver does PIO. PIO is extremely slow and can time out on real hardware with different disk timings. The status bit might flip in a slightly different order. Ensure you have a timeout, and that you never spin forever on a bit.
