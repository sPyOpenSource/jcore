Glossary

Trusted Computing Base

Lesson 2 of the x86 Processor Modes series.

1. The Core Idea

The Trusted Computing Base (TCB) is the set of hardware, firmware, and software that must work correctly for the system's security policy to hold. If any component in the TCB is buggy or compromised, the entire system's security is lost.

Lampson et al. put it succinctly:

A small amount of software and hardware that security depends on, distinguished from a much larger amount that can misbehave without affecting security.

In your JCore kernel, the TCB answers: "What must be bug-free for Domain A to be isolated from Domain B?"

2. What's in JCore's TCB?

ComponentIn TCB?Why
CPU (Ring 0–3 enforcement)YesHardware enforces segment/ page protection — if broken, isolation fails.
GDT / segment descriptorsYessegments.h defines which segments can access what. A bad descriptor lets Ring 3 code into Ring 0.
Kernel C code (src/)YesMemory manager, scheduler, portal system — all run in Ring 0 with full power.
AOT compiler (ByteCodeTranslater)YesProduces native code from Java bytecode. If it generates wrong code, it bypasses all security.
Java standard library classesNoThey run in user domains, constrained by the kernel's protection mechanisms.
User Java applicationsNoSandboxed — their misbehaviour is contained by the kernel, portals, and Ring 3 isolation.

3. The Ring 0 / Ring 3 Boundary

The TCB boundary is enforced by x86 privilege levels. Your segments.h:

#define KERNEL_CS  0x10   /* index 2, RPL=0 → Ring 0 */
#define USER_CS    0x43   /* index 4, RPL=3 → Ring 3 */

Ring 0 code (the kernel) can execute privileged instructions (lgdt, mov cr0, out to I/O ports). Ring 3 code (user Java domains) cannot — if it tries, the CPU raises a #GP (General Protection Fault).

This is hardware-enforced TCB isolation. The kernel doesn't have to check every instruction; the CPU does it.

4. Why TCB Size Matters

A smaller TCB is easier to audit and verify. The seL4 microkernel (∼8,700 lines of C) has a formal mathematical proof of correctness. JCore's kernel is larger — more code means more potential bugs, which means more attack surface.

JCore's architecture reduces its effective TCB in one clever way: the Java type system. If the AOT compiler produces correct code, then Java type safety is part of the TCB — array bounds checks, null checks, and access modifiers are enforced by the compiled code itself.

But the AOT compiler is itself part of the TCB. If it has a bug, it could generate Ring 0-level code from untrusted bytecode. This is the trusted compiler problem (also known as Ken Thompson's "Reflections on Trusting Trust").

5. Boot Chain of Trust

A system's TCB doesn't start at the kernel entry point. It starts at power-on:

CPU reset → BIOS/UEFI → GRUB → JCore kernel → Domain Zero → User domains
   (hardware)    (firmware)  (bootloader)  (kernel C)   (Java init)  (apps)

Each stage must verify the next (or at least not introduce vulnerabilities before the next stage can enforce security). In real mode (Lesson 1), the CPU has no protection — everything runs at effectively Ring 0. Security only begins once CR0.PE is set, the GDT is loaded, and the CPU enters protected mode.

Key insight: Before CR0.PE is set, there is no TCB enforcement — the system relies entirely on the correctness of the bootloader. This is why secure boot systems (UEFI Secure Boot, measured boot) extend the TCB concept to the firmware layer.

6. Thought Experiment

Look at src/portals.c and src/domain.c in JCore. Portals are the mechanism for cross-domain communication — Domain A calls a method on an object in Domain B. The portal system must enforce: can Domain A call this method?

Questions to ask yourself:

  • Is the portal dispatch code part of the TCB? (Hint: it runs in Ring 0.)
  • What happens if a portal descriptor is corrupted?
  • Does the Java access modifier (public/private) provide any protection across domain boundaries, or is that entirely in the kernel?
