Lesson 1: The Raspberry Pi Boot Chain

Why the GPU wakes up before the CPU — and what that means for your kernel.

This is not a PC

On an x86 PC, the CPU powers on and immediately starts executing BIOS/UEFI code at the reset vector. The CPU is the root of trust.

On a Raspberry Pi, the VideoCore GPU powers on first. The ARM CPU is held in reset. The GPU sets up the system, loads firmware, and then releases the ARM cores to run your kernel. This inverted boot order is the single most important fact about RPi bare-metal development.

Why? Broadcom designed the BCM2835 (and successors) for set-top boxes. In that world, the GPU needs to start first to render a UI instantly. The ARM CPU is secondary. The Raspberry Pi Foundation built the Pi around this chip — the boot order is a legacy of that design choice.

The Boot Chain (RPi 4)

VideoCore VI (ROM)
Stage 1: ROM Bootloader
Mask ROM executes on GPU. Checks OTP, nRPIBOOT pin. Reads SPI EEPROM for Stage 2.
↓
VideoCore VI (EEPROM)
Stage 2: SPI EEPROM Bootloader
Configurable bootloader. Tries BOOT_ORDER (SD → USB → Network → NVMe). Loads start4.elf.
↓
VideoCore VI (RAM)
Stage 3: start4.elf (GPU Firmware)
Reads config.txt. Applies device tree overlays. Sets memory split. Loads DTB and kernel8.img into RAM. Releases ARM from reset.
↓
ARM Cortex-A72
Stage 4: Your Kernel
Executes at 0x80000 (AArch64). x0 = DTB pointer. All four cores spinning; only core 0 runs.

Legacy Chain (RPi 3 and earlier)

RPi 1-3 use the same concept but with SD-card-based Stage 2 instead of EEPROM:

GPU ROM → bootcode.bin (from SD) → start.elf (from SD) → config.txt → kernel8.img (AArch64 at 0x80000)

The bootcode.bin file sits on the SD card's FAT32 boot partition. On RPi 4+, this is replaced by the SPI EEPROM — no bootcode.bin needed (or possible).

Model Comparison

RPi 1 / 2 / 3 (BCM2835/6/7)

  • Stage 2: bootcode.bin on SD
  • Stage 3: start.elf on SD
  • AArch32: kernel.img at 0x8000
  • AArch64 (3+): kernel8.img at 0x80000
  • Config: config.txt on boot partition
  • Secondary cores: spin in armstub8

RPi 4 (BCM2711)

  • Stage 2: SPI EEPROM (no bootcode.bin)
  • Stage 3: start4.elf on SD
  • AArch64 only for kernel: kernel8.img
  • AArch32 via kernel7l.img at 0x8000
  • BOOT_ORDER configurable in EEPROM
  • GIC-400 interrupt controller

What Your Kernel Sees at Entry

When start.elf finishes and releases the ARM, it enters your kernel with:

RegisterValue
x032-bit pointer to the Device Tree Blob (DTB) in memory
x10
x20
x30
x4Kernel entry point (_start)
spUndefined — you must set your own stack
Key difference from UEFI: With UEFI (your EFI_AARCH64 project), the firmware provides a rich boot services API (alloc pages, open files, load images). On bare-metal RPi, start.elf gives you nothing at runtime — just the DTB address in x0. No runtime services, no protocols. You talk to hardware directly via MMIO.

What Goes on the SD Card

For a minimal AArch64 bare-metal kernel, your SD card boot partition (FAT32) needs:

FilePurpose
start4.elfGPU firmware (for RPi 4; use start.elf for older) — from RPi firmware repo
fixup4.datMemory fixup file (paired with start4.elf)
bcm2711-rpi-4-b.dtbDevice tree blob for your board
config.txtConfiguration: tell firmware to boot 64-bit and name your kernel
kernel8.imgYour kernel — raw AArch64 binary, loaded at 0x80000

Minimal config.txt for AArch64 boot:

arm_64bit=1
kernel=kernel8.img
# Optional: enable UART on GPIO 14/15 for debug
enable_uart=1
# Optional: GPU memory (16MB is enough for headless)
gpu_mem=16

Your Existing rpi2/ Code — What Needs to Change

Your rpi2/ directory has a 32-bit AArch32 boot stub for RPi 2 (boot.S at 0x8000). For an AArch64 kernel on RPi 3 or 4, you need:

  1. Load address: 0x80000 instead of 0x8000
  2. AArch64 instructions: Rewrite boot.S in AArch64 assembly
  3. Exception levels: You start at EL2 (or EL3 with armstub), not EL1 — may need to drop down
  4. Peripheral base: 0xFE000000 for RPi 4, 0x3F000000 for RPi 3
  5. Output format: Raw binary, not ELF. Link with -T link.ld -nostdlib -Wl,-N -o kernel8.elf && objcopy -O binary kernel8.elf kernel8.img

Try It: Trace the Boot Chain on Your Pi

If you have a Raspberry Pi 4, you can see Stage 2 in action by enabling UART debug from the bootloader:

  1. Add to config.txt: BOOT_UART=1
  2. Connect a USB-UART cable to GPIO 14 (TX) and 15 (RX), GND to GND
  3. Open a serial terminal at 115200 baud
  4. Power on — you'll see bootloader debug output before your kernel even starts

This is the first real "skill" of RPi bare-metal: getting UART output from the bootloader itself, which gives you a window into every stage before your code runs.
