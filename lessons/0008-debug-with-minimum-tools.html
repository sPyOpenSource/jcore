Debugging with Minimum Tools: The LED Interface

The "Blind" Developer's Dilemma

Imagine your kernel crashes. The screen is black. The serial port is silent. You have no debugger attached. How do you know if the CPU is in a while(1) loop, a HardFault, or if it simply didn't start?

This is where LED Signaling becomes your primary diagnostic tool.

1. Checkpoint Debugging

Instead of printf("Reached step 1"), you use LED_ON(1).

void kernel_main() {
    led_on(LED_0); // Milestone: Main reached
    init_mmu();
    led_on(LED_1); // Milestone: MMU initialized
    init_scheduler();
    led_on(LED_2); // Milestone: Scheduler ready
}

By observing which LED is the last to light up, you narrow the crash location to a specific function call.

2. Liveness (The Heartbeat)

A system that isn't blinking is a dead system. Implementing a "heartbeat" in your idle task or a timer interrupt proves that the CPU is still executing instructions and that interrupts are functioning.

3. Signaling Crash Types

Different failure modes should have different visual signatures:

  • Steady ON: Normal operation / Waiting.
  • Slow Blink: Idle / Heartbeat.
  • Rapid Blink: Panic / HardFault.
  • Alternating Blink: Memory Error / Stack Overflow.

Summary

Minimum-tool debugging is about converting Internal State $\rightarrow$ Visual Patterns. It requires discipline in how you place your signals, but it is the only way to debug the most critical, early-stage boot code.
