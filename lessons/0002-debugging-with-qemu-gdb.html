Lesson 2: Debugging Bare-Metal with QEMU + GDB

When "print statements" aren't enough — step through your kernel instruction by instruction.

The Bare-Metal Debugging Pyramid

On an OS, you have crash dumps, strace, valgrind. On bare metal, you have nothing. Build your debugging stack from bottom up:

LevelToolWhen to use
1 — DeepQEMU GDB stub (-s -S)Code crashes at startup, wrong register values, need to see execution
2 — TraceQEMU -d in_asm,intKernel runs but takes unexpected path; want a full instruction log
3 — PrintUART / GPIORuntime state dumps, "I got here" markers, register snapshots
4 — BareGPIO LED blinkNo UART? Blink an LED from key code paths — one blink per reach

Technique 1: QEMU GDB Stub

This is your most powerful tool for the kernel-won't-boot scenario. QEMU exposes a GDB remote stub: you pause the VM, connect GDB, and step through your code as if it were a normal user-space program.

Launch QEMU with debug server

$ qemu-system-aarch64 -M raspi2b \
-device loader,file=kernel7-uart.img,addr=0x8000,force-raw=on \
-serial stdio -display none \
-s -S

-s opens a GDB server on TCP port 1234. -S freezes the CPU immediately — no code executes until you tell GDB to continue.

Connect GDB

$ gdb-multiarch kernel.elf
(gdb) target remote localhost:1234
Remote debugging using localhost:1234
0x00000000 in ?? ()

The CPU is frozen at address 0 (the reset vector). Your kernel is already loaded at 0x8000. Set a breakpoint and go:

(gdb) break *0x8000
Breakpoint 1 at 0x8000: file boot_fixed.S, line 12.
(gdb) continue
Continuing.

Breakpoint 1, _start () at boot_fixed.S:12
12 mrc p15, 0, r5, c0, c0, 5

You've hit your kernel's entry point. Now you can:

CommandEffect
stepi / siExecute one instruction, then pause
nexti / niStep over (skip) one instruction
continue / cRun until next breakpoint
info registersShow all CPU registers
x/16x 0x8000Examine 16 hex words at address 0x8000
disasDisassemble around current PC
layout regsEnable TUI mode with register pane
info threadsList all 4 CPU cores (raspi2b)
thread NSwitch to CPU core N

Skill: Step Through Your Kernel

Your kernel7-uart.img does: mrc → and → cmp → bne → ldr → mov sp → ... → blx main → UART init → print → echo loop. Use stepi to trace each instruction. Watch $r5 after the mrc — that's your CPU ID (should be 0 on core 0).

Technique 2: QEMU Trace Flags

When GDB is overkill, QEMU's built-in tracing gives you a quick log of everything that happened:

FlagLogs
-d in_asmEvery instruction translated (one line per basic block)
-d intInterrupts: when they fire and the return address
-d cpu_resetCPU state at every reset — useful for crash analysis
-d mmuMMU translations (once you enable the MMU)
-D logfileWrite trace to a file instead of stderr
$ qemu-system-aarch64 -M raspi2b \
-device loader,file=kernel7-uart.img,addr=0x8000,force-raw=on \
-d in_asm -D /tmp/trace.log -serial stdio -display none
$ head -40 /tmp/trace.log

Technique 3: UART as Debug Output

You already have this. The key pattern is annotated checkpoints — not just "it got here" but state dumps:

void check_reg(const char* label, uint32_t val) {
    uart_puts("*** ");
    uart_puts(label);
    uart_puts(" = 0x");
    print_hex32(val);   // write a hex printer
    uart_puts(" ***\r\n");
}

Call it from boot_fixed.S before jumping to main to dump $r0 (DTB pointer on real hardware!) and $r1 (machine ID).

Make a hex printer now. It's your most reusable debug tool. Write print_hex32(uint32_t val) that shifts out 8 hex nibbles via UART. Put it in a shared debug.h that every future lesson can #include.

Technique 4: GPIO LED Blink (for Real Hardware)

When you have no UART cable and no JTAG, blink an LED. One blink = "got to init". Two blinks = "passed init". Fast blink = "in the main loop".

void blink_ok(void) {
    for (int i = 0; i < 3; i++) {
        GPIO_SET = 1 << 21;   // LED on
        delay(1000000);
        GPIO_CLR = 1 << 21;   // LED off
        delay(1000000);
    }
}

Three quick blinks = "I'm alive at this point". This is how bare-metal debugging started before UART was standard.

Your Turn: GDB Lab

  1. Build make -C rpi2 kernel.elf (with debug symbols, add -g to CFLAGS)
  2. Launch QEMU with -s -S
  3. In another terminal: gdb-multiarch rpi2/kernel.elf -ex 'target remote :1234'
  4. Set a breakpoint: b main
  5. c — watch it stop at main
  6. layout regs — see registers live as you step
  7. si three times, watch the UART registers get written

If gdb-multiarch isn't installed: brew install gdb or use arm-none-eabi-gdb from the Arm toolchain.
