Lesson 11: JVM Garbage Collection III
GC optimization — trade-offs, metrics, and log analysis

Mission: JCore ships four real collectors in src/Memory/gc_*.c. "Optimizing" GC means understanding the three-way trade-off between pause time, throughput, and memory footprint — then choosing the collector (or tuning it) for your workload. This lesson teaches you to read GC logs, measure the axes, and map JCore's collectors to their HotSpot counterparts.

What "GC optimization" actually means

In your kernel (jxmalloc), optimization meant "make allocation faster" or "reduce fragmentation." In a GC, you cannot optimize one axis without hurting another:

AxisWhat it meansJCore metric
Pause time (latency)How long mutators are stopped during collectionTime field in gc_printInfo output
Throughput% of CPU time spent running mutator vs GC1 - (total GC time / total runtime)
Memory footprintHeap size needed for a given allocation rateheap(used) / heap(total) in printInfo

No free lunch. A collector that pauses for 1ms (low latency) typically needs more heap (high footprint) or uses more CPU for concurrent work (lower throughput). The "optimal" choice depends entirely on what your application values.

Reading JCore GC logs

When you run JCore with NOTICE_GC and MEASURE_GC_TIME defined, you get output like:

GC IN  3 (SystemDomain) started

GC IN  3 finished
   GC Info for SystemDomain (   3)
      Runs:   5, Time:  1234567, Collected Bytes: 1048576
heap(used ): 0x100000...0x105000 (current=0x104800)
heap(other): 0x200000...0x205000 (current=0x200000)
total: 20480, used: 5120, free: 15360

Key fields to extract per-collection:

  1. Time — pause duration in microseconds (from MEASURE_GC_TIME)
  2. Collected Bytes — memory reclaimed this cycle
  3. Runs — cumulative collection count for this domain
  4. Collector-specific lines — heap ranges, word counts, chunk stats

Derived metrics you should compute

MetricFormulaWhat it tells you
Allocation rateCollected Bytes / time since last GCHow fast mutator creates garbage
Collection frequency1 / time between GCsHow often you pause
Mean pauseΣ pause / countTypical stop-the-world cost
P95/P99 pauseSort pauses, pick 95th/99th percentileWorst-case latency spikes
Throughput %100 * (1 - total_GC_time / total_runtime)Mutator CPU share
Survival rate(heap_after - heap_before) / allocated_since_last_GCHow much data survives (promotion pressure)

Your allocation rate is the driver. If allocation rate doubles, either pause time doubles (same heap), or you need 2× heap (same pause). The collector choice determines which knobs you have.

Diagnosing common GC patterns from logs

Pattern: "Pause time keeps growing"

Symptoms: Time field increases steadily; Collected Bytes stays flat.

Causes: Heap too small → more frequent GCs with more live data each time. Or: memory leak (survival rate → 100%).

JCore action: Check heap(used) trend in printInfo. If it grows monotonically, you have a leak in the mutator, not a GC problem.

Pattern: "Full GC every N collections"

Symptoms: Periodic massive Time spike; Collected Bytes is huge.

Causes: In generational terms: promotion failure (old gen full). In JCore's gc_org: from-space fills up and everything is live.

JCore action: Look at total: X, used: Y, free: Z — if free is tiny after GC, your heap is undersized for the live set.

Pattern: "High throughput but occasional huge pauses"

Symptoms: Most Time values small, but rare spikes.

Causes: Incremental/region-based collector (gc_chunked) doing a full compaction cycle.

JCore action: Check gc_chunked_printInfo chunk list — how many chunks? Are they fragmented?

Mapping to HotSpot: the same trade-offs, different names

GoalHotSpot choiceJCore analogueWhen to pick
Lowest pause, large heap OK ZGC / Shenandoah Not in JCore yet (concurrent relocation) Interactive apps, strict SLAs
Max throughput, batch workloads Parallel GC (-XX:+UseParallelGC) gc_org (if young) / gc_compacting (if old) Batch jobs, data processing
Balanced, moderate heap G1 (-XX:+UseG1GC) gc_chunked (regions + incremental) Most server apps
Minimal footprint, single-threaded Serial GC gc_org or gc_compacting Embedded, small heaps

Try it yourself

  1. Run JCore with NOTICE_GC and MEASURE_GC_TIME. Capture a log. Compute: mean pause, P95 pause, allocation rate, throughput.
  2. In gc_org.c:2207, trace the two heaps (heap/heap2). Why does gc_org need 2× memory? What happens if you allocate faster than GC can copy?
  3. Compare gc_compacting_printInfo() and gc_bitmap_printInfo(). Both use 1× heap. What does gc_compacting pay for compaction that gc_bitmap doesn't? (Hint: sliding vs sweeping)
  4. Open gc_chunked.c:468. How does the chunk list structure let gc_chunked do incremental work? What would happen if you added a new chunk mid-GC?
