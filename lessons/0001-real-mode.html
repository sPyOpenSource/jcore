Real Mode — The 16-bit Starting World

Lesson 1 of the x86 Processor Modes series.

1. The Boot Story

When you press the power button on an x86 machine, the CPU wakes up in real mode — a 16-bit compatibility mode that imitates the Intel 8086 from 1978. Every x86 CPU (up to the latest Intel Core and AMD Ryzen) starts here. This is why your machine can still run DOS.

The boot flow goes:

Power-on → CPU in real mode → BIOS POST → BIOS loads bootloader → bootloader → ...

In JCore, the bootloader is GRUB. GRUB receives control from the BIOS, sets up its own environment, then switches to protected mode and jumps to your kernel's entry point. By the time crt0.S's _start runs, the CPU is already in 32-bit protected mode.

But the realmode binary and the prot_to_real / real_to_prot functions in asm.S prove that JCore still needs real mode for certain tasks.

3. Memory Addressing: Segment:Offset

The 8086 had 16-bit registers but wanted to address 1 MB (20 bits). The solution: combine a segment register and an offset register to form a 20-bit address.

Physical address = (segment << 4) + offset
Example:  0x12F3:0x4B27  →  (0x12F3 × 16) + 0x4B27  =  0x17A57

This gives a 20-bit address space: 220 = 1,048,576 bytes = 1 MB. Each segment is 64 KB (16-bit offset), but you can change the segment base to reach anywhere in the 1 MB space.

The six segment registers are: CS (code), DS (data), SS (stack), ES (extra), FS and GS (general-purpose). This is a key difference: in protected mode, these registers hold selectors (indices into the GDT), not base addresses. In real mode, they are the base (shifted left 4 bits).

4. Real Mode in JCore

Your codebase switches back to real mode for one reason: BIOS interrupts. When the kernel needs to query or set video modes, it must call int 0x10 — the BIOS video interrupt. BIOS runs in real mode.

Look at src/Assembly/asm.S:

ENTRY(vesa2_detect)
    call   prot_to_real   ; switch to real mode
    .code16
    movw   $0x4F00, %ax
    int    $0x10           ; VESA BIOS call — only works in real mode!
    DATA32 call   real_to_prot  ; switch back
    .code32

The prot_to_real function:

  • Saves the protected-mode stack pointer
  • Loads 16-bit segment selectors (KERNEL_16_DS)
  • Far-jumps to a 16-bit code segment (KERNEL_16_CS)
  • Clears CR0.PE — the single bit that separates real mode from protected mode
  • Far-jumps to realcseg with segment registers set to 0 (real mode style)

5. Pros and Cons of Real Mode

Pros (why it still matters)

  • BIOS services: interrupts for disk I/O (int 0x13), video (int 0x10), keyboard, ACPI. The firmware installs these handlers — you don't need your own drivers.
  • Simplicity: no GDT, no page tables, no privilege checks. The CPU just fetches and executes.
  • Speed for simple tasks: fewer descriptor lookups per memory access.

Cons (why we leave it)

  • 1 MB limit: not enough for a modern kernel. JCore loads at 2 MB (linker.ld: . = 2M).
  • No memory protection: any program can overwrite the kernel, BIOS data, or other programs. No isolation.
  • 16-bit defaults: 64 KB segment limit is painful — complex segment arithmetic required for large data.
  • No hardware multitasking support: no TSS, no ring transitions.
  • No virtual memory: every address is physical, paging is off.

6. Check Your Understanding

Look at src/Headers/segments.h:

#define KERNEL_CS     0x10
#define KERNEL_16_CS  0x20

The value 0x10 is a segment selector. In binary: 0000 0000 0001 0|0|00 — index 2, TI=0 (GDT), RPL=0 (Ring 0). JCore's GDT entry at index 2 is the 32-bit code segment.

0x20 is index 4: the 16-bit code segment descriptor (with D/B = 0, meaning 16-bit operand size by default).

Key insight: The CPU doesn't "change modes" when CR0.PE flips. It interprets segment registers differently. In real mode, CS = raw base << 4. In protected mode, CS = index into GDT. The mode switch is a reinterpretation of the same bytes.
