Lesson 6: Boot Stages
From GRUB to Java — the JCore boot path

Mission: You're building the JCore kernel. Understanding the boot path from CPU reset through to the first Java thread lets you trace every subsystem's initialization order, know where to add new features, and debug early boot failures.

Overview

JCore's boot path passes through five distinct stages, each in a different layer of the system:

Each stage is irreversible — by the time the next stage starts, the previous stage's functions are no longer called. The boot path is a strict partial order.

Stage 0: CPU Reset → GRUB (not JCore code)

When the CPU powers on, it begins in real mode at address 0xFFFF0. The BIOS initializes hardware, then loads GRUB. GRUB performs the real → protected mode transition (setting CR0.PE, loading a GDT, far-jumping to 32-bit code), then loads the JCore kernel binary from disk and hands off via the Multiboot2 protocol.

By the time _start executes, the CPU is already in 32-bit protected mode, paging is disabled (CR0.PG = 0), and ebx holds the physical address of the Multiboot2 info structure.

Key code: Not JCore code. See linker.ld — the kernel is linked at 2 MB physical, and GRUB loads it there because the Multiboot2 header (at .multiboot_header) declares it.

Stage 1: Assembly Entry (crt0.S)

crt0.S is the first JCore code to execute. It does exactly three things:

  1. Set the stack pointer to base_stack_end (defined in the linker script as the top of .bss + stack space).
  2. Preserve Multiboot info — pushes ebx (Multiboot2 physical address) and eax (magic number) onto the stack, then calls multiboot_main.
  3. Scan for framebuffer tag — walks the Multiboot2 tag list looking for tag type 8 (framebuffer). If found, draws a red test pattern directly to the framebuffer memory.

Notice what crt0.S does not do:

  • No GDT setup (GRUB already set one up)
  • No paging setup (JCore doesn't use paging)
  • No interrupt setup (that comes in Stage 2)

Code location: src/Assembly/crt0.S:33-53
Key line: call multiboot_main — the handoff from assembly to C.

Stage 2: C Low-Level Init (multiboot_main)

Found in src/multiboot.c:478-532. This stage establishes the minimum C runtime environment:

  1. Validate Multiboot2 magic (0x36D76289) — panics if wrong bootloader.
  2. Clear interrupts (cli), initialize serial port.
  3. Clear VGA text screen (writes spaces to 0xB8000).
  4. Set up GDT (base_gdt_init(), base_gdt_load()) — JCore's own GDT replaces GRUB's. See asm.S for the GDT entries and segments.h for selectors.
  5. Set up IDT (idt_load()) — installs handlers for traps and IRQs.
  6. Configure debug registers — sets DR6 and breakpoints 0/1 for performance monitoring.
  7. Initialize heap (jxmalloc_init()) — enables dynamic memory allocation.
  8. Call main() — hands off to the kernel proper.

Code location: src/multiboot.c:478-531
Cross-reference: Lesson 2: TCB — the GDT and IDT setup establishes the foundation of the TCB, defining the ring-0/ring-3 boundary.

Stage 3: Kernel Subsystem Init (main())

This is the largest initialization stage. Found in src/main.c:63-200. It progresses in a careful order, each subsystem depending on the ones before it:

OrderCallWhat it does
1multiboot_get_module()Finds the boot module (a ZIP archive) from the Multiboot2 info and hands it to zip_init().
2pic_init_pmode()Initializes both 8259A PICs (Master at 0x20, Slave at 0xA0), remaps IRQ vectors to 0x20-0x2F to avoid CPU exception overlap, sets automatic EOI.
3init_irq_data()Allocates per-IRQ data structures (handlers, counters).
4ser_enable_break()Enables serial break detection for debugging.
5init_domainsys()Allocates domain descriptor memory pool, creates DomainZero — the root domain that owns all kernel resources.
6atomicfn_init()Initializes atomic operation support (CAS, memory barriers) needed for lock-free data structures.
7threads_init()Initializes the thread system: run queues, idle threads, scheduler data.
8portals_init()Initializes the cross-domain communication system (portals).
9createObjectClassDesc()Creates the java.lang.Object class descriptor — the root of the Java type system.
10createThread(dummy_entry_point)Creates the idle thread — the first thread in the system, used when nothing else is runnable.
11initPrimitiveClasses()Registers class descriptors for boolean, int, long, etc.
12createThread(start_domain_zero)Creates the DomainZero initial thread — the first real thread that will run Java code. Calls thread_exit() (never returns).

  • Lesson 3: MMU — JCore does not enable paging. It uses pure segmentation for protection.

Stage 4: DomainZero Java Thread (start_domain_zero)

Found in src/Interface/zero.c:246-437. This is where the system transitions from "C kernel" to "kernel + Java runtime".

Low-level initialization

  1. APIC detection — checks for a local APIC. If found: installs APIC IRQ handlers, enables the APIC, and calibrates the APIC timer.
  2. Set up system timer (setTimer()) — the PIT (8253) or APIC timer, depending on configuration.
  3. Enable interrupts (sti()) — from this point forward, the kernel is interrupt-driven.

Library loading

  1. Load zero.jll — the core JX runtime library (written in Java, compiled to JX native code). Contains the implementation of all portal interfaces (Domain, Memory, CPU, IRQ, Scheduler, Naming, etc.).
  2. Link portals — init_zero_from_lib() initializes ~25 portals, one per kernel service. Each portal pairs a Java interface with a C implementation.
  3. Run class constructors for zero.jll — static initializers execute, linking Java classes to their native implementations.
  4. Load jdk0.jll — a minimal Java standard library (String, Array, Math, etc.).
  5. Run class constructors for jdk0.jll.

Domain creation

The function creates a new domain — Domain "Init" — via the DomainManager portal. This is the first Java-level domain:

domainProxy = domainManager_createDomain(dm,
    newString("Init"),       // domain name
    INIT_LIB,                // "AI/AI" — the initial class
    domainZero->initialNamingProxy, ...);

The Init domain gets its own:
- Heap (HEAP_BYTES_INIT)
- Code space (CODE_BYTES_DOMAININIT)
- Scheduler (LowLevelScheduler + HighLevelScheduler per CPU)

Clean exit

The DomainZero initial thread terminates (thread_exit()) — it only exists long enough to bootstrap the Init domain.

Code location: src/Interface/zero.c:246-437
Key concept: zero.jll is what makes JCore "JX" — it's the Java-to-native bridge that lets kernel services be called from Java code via portals.

Stage 5: Init Domain and Beyond

Once the Init domain is running, the system is fully operational. The Init domain:

  1. Runs the Java scheduler — manages thread priorities, time slices, preemption.
  2. Can load additional domains — each domain is an isolated trust boundary.
  3. Eventually loads user-facing services (networking, file systems, the AI subsystem).

This is where the kernel's domain isolation model kicks in — portals mediate all cross-domain communication, and the TCB ensures no domain can escape its sandbox.

Summary: The Boot Path as a Dependency Chain

The boot stages form a strict dependency chain where each stage enables the next:

StageEnablesFile
0. GRUBProtected mode, Multiboot infonot JCore
1. AssemblyC callable (stack, parameters)crt0.S
2. Low-level CGDT, IDT, heapmultiboot.c
3. Kernel subsystemsPIC, domains, threads, portalsmain.c
4. DomainZero JavaJava runtime, JLL librarieszero.c
5. Init domainJava scheduler, user servicesJava (AI/AI)

Each stage has exactly one entry function: assembly → multiboot_main → main → start_domain_zero → domainManager_createDomain.

Things to Try

  1. Trace the path — open crt0.S, multiboot.c:478, main.c:63, zero.c:246 and follow the call chain.
  2. Add a breakpoint at the start of main() in QEMU/GDB — verify that CR0.PG == 0 and you're in protected mode.
  3. Look at the commented-out init_realmode() at main.c:129 — that would have been Stage 3.5, switching back to real mode for VESA framebuffer detection.
