The Heart of the VM: The Fetch-Decode-Execute Loop

At its most fundamental level, every Virtual Machine is just a loop. Whether it's the JVM, the Lua VM, or the Python interpreter, the core of the execution engine is a repetitive cycle that transforms a stream of bytes into actions.

This cycle is known as the Fetch-Decode-Execute loop.

1. The Cycle

Imagine the VM as a tiny computer living inside your real computer. It has its own program counter (PC), its own stack, and its own set of instructions (bytecode). The loop works as follows:

Fetch: Read the next byte of bytecode from the instruction stream at the current program counter.
Decode: Determine which operation that byte represents (e.g., 0x60 might mean aload_0 in the JVM).
Execute: Perform the actual work associated with that operation—pushing a value onto the stack, adding two numbers, or jumping to another part of the code.

2. Implementation in FlintJVM

In flint_execution.cpp, this loop is implemented as a large while loop containing a switch statement. This is the most common pattern for bytecode interpreters.

while (vm->running) {
    uint8_t opcode = vm->fetch_byte(); // FETCH
    
    switch (opcode) { // DECODE
        case OP_IADD: { // EXECUTE
            int v1 = vm->pop();
            int v2 = vm->pop();
            vm->push(v1 + v2);
            break;
        }
        // ... other opcodes ...
    }
}
Note how the fetch_byte() method not only returns the byte but also increments the Program Counter, preparing the VM for the next cycle.

3. The Cost of Indirection

While a switch loop is simple, it comes with a performance penalty: dispatch overhead. Every single instruction requires a branch (the switch), which can be slow because the CPU's branch predictor often struggles to guess which opcode comes next.

Advanced VMs use techniques like Threaded Code or JIT Compilation to eliminate this overhead, but the Fetch-Decode-Execute loop remains the conceptual foundation.
