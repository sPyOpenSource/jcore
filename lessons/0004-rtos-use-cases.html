RTOS Use Cases

Where an RTOS is the right tool — and where it isn't

The Screening Question

If a late answer causes damage — damaged hardware, lost data, a crash, or a human safety risk — you need an RTOS. If a late answer just makes someone wait longer, a GPOS is fine.

Where RTOS Is the Right Choice

Embedded Control (the classic case)

A flight controller reads an IMU at 1 kHz, runs a PID loop, and adjusts motor PWM. If the control loop is delayed by even 10 ms, the drone wobbles or crashes. Linux running on the same CPU could do the math faster, but its scheduling jitter means it occasionally delivers the output late. The RTOS guarantees the deadline.

Same pattern: CNC mills, 3D printers, robot arm controllers, automotive ECU injector timing, ABS brake modulation.

Data Acquisition

A seismic sensor digitizes at 100 kHz. A sample arrives every 10 µs. You need to read it, timestamp it, and buffer it without missing the next sample. A GPOS can miss samples under interrupt load (network, USB). An RTOS guarantees the ISR latency is bounded so no sample is lost.

Same pattern: oscilloscopes, software-defined radios, LIDAR, audio workstations.

Industrial Automation

A PLC reads a pressure sensor every 1 ms. If pressure exceeds a threshold, it must trigger an emergency valve within 5 ms. The safety case requires proof that the worst-case response time is under 5 ms. An RTOS can provide that bound. A GPOS cannot — its worst case is unbounded under heavy load.

Automotive / Aerospace (critical safety)

Modern cars have 100+ ECUs. The brake-by-wire controller must respond to pedal position within a fixed window — not microseconds too late. Aerospace systems (avionics, fly-by-wire) require certification (DO-178C) that proves timing bounds. RTOSs like VxWorks and Integrity are certified for this. Linux is not.

Consumer Electronics (surprising fits)

Many devices you'd think run Linux actually run an RTOS:

  • WiFi/BT firmware — your Broadcom WiFi chip runs ThreadX or FreeRTOS on its internal ARM Cortex-M
  • SSD controller — manages NAND flash wear leveling with tight timing constraints
  • USB-C PD controller — negotiates power delivery with millisecond-level protocol timing

Where RTOS Is the Wrong Choice

ScenarioUse LinuxWhy not RTOS
Web server✓No deadlines; throughput matters; you need TCP/IP, TLS, filesystem
Desktop / laptop✓User interaction tolerates 10–100 ms latency; GPOS provides process isolation, GPU drivers, window system
File server (NAS)✓Storage throughput dominates; disk I/O latency is already variable
Video streaming box✓Media playback buffers absorb jitter; you need GPU, DRM, codecs — none of which exist in an RTOS ecosystem
Prototype / hobby projectDebatableIf you don't have a real deadline, the RTOS wins on simplicity but loses on tooling. Linux wins on libraries but loses on complexity.

The Grey Zone: RTOS on Powerful Hardware

This is where your BBAI project lives. The Cortex-A15 can run Linux effortlessly. Why build an RTOS?

Your project is in the grey zone because:

  • You don't need an RTOS (no hard deadlines)
  • You're building one to learn — the constraint is pedagogical, not functional
  • The BBAI is forgiving hardware (lots of RAM, good docs) for learning OS concepts
This is a legitimate use of an RTOS. Many aerospace and automotive RTOSs started as learning projects that found real deadlines. The skills transfer directly: once you've written a PendSV handler, you can debug one in any RTOS.

Quiz

Q1: A smart thermostat reads temperature every 10 seconds and updates the display. Should it run an RTOS?

Answer: Probably not. 10-second intervals mean scheduling jitter is irrelevant. A simple super-loop on a cheap MCU is fine, or even Linux on a Raspberry Pi if you need WiFi and a touch UI.

Q2: A pacemaker delivers electrical pulses synchronized to the heart's rhythm. Should it run an RTOS?

Answer: Absolutely yes. Late or early pulses can kill. The RTOS must guarantee timing bounds and the entire system must be certified (IEC 62304 Class C).

Q3: If you're using an RTOS but have no hard deadlines, what are you actually getting?

Answer: Simplicity and transparency — deterministic behavior, static allocation, full code auditability. These are valuable even without hard deadlines. This is your BBAI project.
