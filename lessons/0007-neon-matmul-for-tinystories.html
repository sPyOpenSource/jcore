NEON MatMul for TinyStories on BBAI

Making the 15M-parameter transformer actually fast on Cortex-A15

The Bottleneck

A TinyStories-15M transformer has 6 layers, each with:

  • Attention: 4 matrix-vector multiplies (Q, K, V, output projection)
  • FFN: 2 matrix-vector multiplies (gate + up, then down)
  • Embedding: 1 matrix-vector multiply at the end (logits)

Every token does roughly 43 matrix-vector multiplies of size [d_model × d_model] where d_model = 288 for TinyStories-15M. In scalar FP32, that's 43 × 288 × 288 = 3.6M FMAs per token — or 43M FMAs for a 12-token generation.

Scalar performance: The A15 does one FP32 multiply-add per cycle per core at 1.5 GHz = 1.5 GFLOPS theoretical peak. NEON doubles that to 4 FMA/cycle = 6 GFLOPS (4-wide SIMD × 2 for FMA). In practice, you get ~70–80% of peak with good code = ~4.5 GFLOPS. That turns 43M FMAs into ~10 ms per token — 100 tok/s.

NEON on Cortex-A15

The A15 has a NEON unit with:

  • 32× 128-bit registers (q0–q15 or d0–d31, depending on how you count)
  • Each register holds 4× float32
  • VMLA.F32 — fused multiply-accumulate on 4 floats at once
  • 1 FMA/cycle throughput, fully pipelined

You access NEON via intrinsics — C function calls that compile directly to NEON instructions. No inline assembly needed for basic matmul.

// NEON intrinsics header — available in clang's arm-none-eabi target
#include <arm_neon.h>

// Types:
float32x4_t   — 4 floats in one register
float32x2_t   — 2 floats (half register)

// Key operations:
vld1q_f32(ptr)     — load 4 floats from memory
vst1q_f32(ptr, v)  — store 4 floats
vmlaq_f32(acc, a, b)  — acc += a * b (4-wide FMA)
vdupq_n_f32(x)     — broadcast scalar to all 4 lanes
vaddq_f32(a, b)    — 4-wide add

NEON Matrix × Vector

This is the hot loop — nearly all compute time is here. For a weight matrix W[M × K] and input vector x[K], compute y[i] = sum_j W[i][j] * x[j].

Scalar version (baseline):

void matmul_vec(float *y, float *W, float *x, int M, int K) {
    for (int i = 0; i < M; i++) {
        float sum = 0.0f;
        for (int j = 0; j < K; j++)
            sum += W[i * K + j] * x[j];
        y[i] = sum;
    }
}

NEON version (4× unrolled):

#include <arm_neon.h>

void matmul_vec_neon(float *y, float *W, float *x, int M, int K) {
    for (int i = 0; i < M; i++) {
        float32x4_t acc = vdupq_n_f32(0.0f);
        float *w_row = W + i * K;
        int j = 0;
        // Process 4 floats per iteration
        for (; j + 4 <= K; j += 4) {
            float32x4_t w = vld1q_f32(w_row + j);
            float32x4_t xv = vld1q_f32(x + j);
            acc = vmlaq_f32(acc, w, xv);
        }
        // Reduce 4-lane accumulator to scalar
        float32x2_t sum = vpadd_f32(vget_low_f32(acc), vget_high_f32(acc));
        float result = vget_lane_f32(sum, 0) + vget_lane_f32(sum, 1);
        // Handle remaining elements (K not divisible by 4)
        for (; j < K; j++)
            result += w_row[j] * x[j];
        y[i] = result;
    }
}

Performance comparison (theoretical, d_model=288):

Scalar:   288 MACs × 1 MAC/cycle = 288 cycles/row × 288 rows = 83K cycles/token-layer
NEON:     288/4 = 72 MACs × 1 MAC/cycle = 72 cycles/row × 288 rows = 21K cycles/token-layer
Speedup:  ~4× for the matmul, ~3× overall (matmul is ~80% of total compute)

Going Further: 2× More with Prefetching

The A15 has a 32 KB L1 cache. A weight row is 288 × 4 = 1152 bytes. The entire layer's weights don't fit in L1 (6 layers × 4 matrices × 1152 bytes = too much), but one matrix does fit. The bottleneck is loading weights from L2 (1 MB shared).

You can prefetch the next row while computing the current one:

void matmul_vec_neon_prefetch(float *y, float *W, float *x, int M, int K) {
    for (int i = 0; i < M; i++) {
        float32x4_t acc = vdupq_n_f32(0.0f);
        float *w_row = W + i * K;
        // Prefetch next row
        if (i + 1 < M)
            __builtin_prefetch(W + (i + 1) * K, 0, 3);
        int j = 0;
        for (; j + 4 <= K; j += 4)
            acc = vmlaq_f32(acc, vld1q_f32(w_row + j), vld1q_f32(x + j));
        // ... remainder handling (same as above)
    }
}

Bringing It Into Your RTOS

Replace llama2.c's scalar matmul() with the NEON version. The calling convention is the same — just swap the function pointer or rename.

// In llama2.c, find this function and replace it:
// static void matmul(float *xout, float *x, float *w, int n, int d) {
//     for (int i = 0; i < d; i++) { ... scalar ... }
// }

// Your replacement:
static void matmul(float *xout, float *x, float *w, int n, int d) {
    matmul_vec_neon(xout, w, x, d, n);
}
Compiler flags: clang needs -mfpu=neon -mfloat-abi=hard to emit NEON instructions. Add these to your CFLAGS in the Makefile. Without them, arm_neon.h intrinsics will still compile but generate calls to soft-float library functions instead of NEON — useless.

What to Do Right Now

  1. Test NEON on your host: You can compile NEON intrinsics on your Mac (ARM64 Mac) with clang -O2 -march=armv8-a+simd to verify the code works.
  2. Cross-compile for BBAI: Add -mfpu=neon -mfloat-abi=hard to your Makefile's CFLAGS.
  3. Benchmark the matmul: Write a tiny test that times one matrix-vector multiply (288×288) with and without NEON, print results to UART.
  4. Link TinyStories-15M weights: Download stories15M.bin (60 MB), convert to a C array, and link it in.

The NEON intrinsic version alone is ~3× faster than scalar. That's the difference between "cute demo" and "actually usable."

Reference: Full NEON MatMul for llama2.c

Replace llama2.c's matmul() with this:

#include <arm_neon.h>

static void matmul(float *xout, float *x, float *w, int n, int d) {
    // xout[d] = w[d][n] @ x[n]   (weight matrix × input vector)
    for (int i = 0; i < d; i++) {
        float32x4_t acc = vdupq_n_f32(0.0f);
        float *w_row = w + i * n;
        int j = 0;
        for (; j + 4 <= n; j += 4)
            acc = vmlaq_f32(acc, vld1q_f32(w_row + j), vld1q_f32(x + j));
        float32x2_t sum = vpadd_f32(vget_low_f32(acc), vget_high_f32(acc));
        float result = vget_lane_f32(sum, 0) + vget_lane_f32(sum, 1);
        for (; j < n; j++)
            result += w_row[j] * x[j];
        xout[i] = result;
    }
}

That's the entire NEON port. One function. ~15 lines. 3× speedup.
