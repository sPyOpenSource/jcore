Lesson 9: JVM Garbage Collection I
What is garbage? — the reachability model

Mission: JCore is a JVM — every new it executes allocates an object, and no one ever calls free on it. JCore already ships a real garbage collector in src/Memory/gc_*.c. Before we read that code, we need the one idea everything else hangs on: what counts as garbage?

The shift from malloc to new

In your kernel, memory is manual. You pair every jxmalloc(size) with a jxfree(addr, size) — and you saw in Lesson 7 how fragile that is: pass the wrong size to jxfree and the bitmap corrupts.

The JVM is different. A Java program calls new millions of times and never frees anything. So where does the memory go? The answer is that garbage collection is not an optimization — it is the only memory reclamation mechanism. The runtime decides what is dead and reclaims it, automatically.

You already built half of this. In src/malloc.c:601, malloc_code() is a bump allocator: it hands out the next N bytes and never frees individually — memory is reclaimed in bulk when a domain dies. That "allocate everything, clean up later" shape is exactly how a GC heap works. The hard part isn't allocation (a bump pointer). The hard part is deciding what to clean up.

The definition: garbage = unreachable from roots

An object is garbage if and only if it cannot be reached by following references from a set of root objects. That's it. Nothing the program "says" matters — no explicit free, no count. Purely graph reachability.

Roots ──pointers──▶ live objects ──...──▶ more live objects

                              ░░░░░░ = garbage (no path from any root)

Why does this definition work? Two properties:

  1. No dangling pointers. A reachable object is in use, so it must stay. An unreachable object can never be seen again, so it can be freed or even moved.
  2. Cycles get collected. Two objects pointing at each other but with no path to a root are still garbage. (Reference counting — the other main scheme — leaks exactly this case. We'll compare in the next lesson.)

What are the roots?

In HotSpot the root set is:

RootWhere it lives
Local variables & operand stackEach active thread's stack (at safepoints)
Static fieldsLoaded classes' Class objects
JNI referencesNative code's GlobalRef handles
JIT register contentsLive registers of compiled frames

JCore's collector scans the same classes of roots. In gc_org_gc() at src/Memory/gc_org.c:1084, before it moves anything, it walks every thread and scans its stack:

for (t = domain->threads; t != NULL; t = t->nextInDomain) {
    if (t == domain->gc.gcThread) continue;
    if (t->isInterruptHandlerThread) continue;
    if (t->state == STATE_AVAILABLE)   continue;
    gc_org_scan_stack(domain, t, JNI_FALSE);   /* roots on the stack */
}
/* ...then statics of loaded classes (scan_class_org) */

This is exactly HotSpot's "scan thread stacks, then statics" recipe — because JCore is a JVM, its GC has the same job. That one page is your anchor: GC = find roots, walk everything reachable, treat the rest as garbage.

Code: src/Memory/gc_org.c:1084-1203 — gc_org_gc() root scanning. Note it also scans "classes" statics right after the stack loop.

Why this matters for everything that follows

Every collector in the JVM (Serial, Parallel, CMS, G1, ZGC, Shenandoah) is a different answer to one question: how do you find the unreachable objects, and what do you do with them? But they all agree on the definition. Once you can look at any object graph and determine liveness by hand, the algorithms are just engineering.

Three families you'll meet, all starting from this definition:

FamilyHow it finds garbageWhat it does after
Mark-sweepTrace from roots, mark reachableSweep: free unmarked objects in place
CopyingTrace from rootsMove survivors to a fresh space (JCore's gc_org.c)
Mark-compactTrace from roots, markSlide survivors together, no holes

Check yourself

1. Root R points to A. A points to B. B points to C. Nothing else exists. Which objects are garbage?

Every object is reachable from R via a reference chain (R→A→B→C), so none is garbage. Garbage = unreachable, not "old" or "unused".

2. R points to A. A points to B. B points back to A. C and D point to each other but nothing points to them. Which objects are garbage?

A↔B is a reachable cycle (you get there from R), so it lives. C↔D is a cycle with no path to any root — exactly the cycle that reference counting leaks. Reachability kills it.

3. In gc_org_gc(), which words on a thread stack does the collector treat as roots?

Only words that actually hold references are roots. The hard part is knowing which words those are — JCore uses stack maps emitted by its compiler to find them.

Try it yourself

  1. Open src/Memory/gc_org.c and find gc_org_init() (line 2221). Note the two heap halves (from-space and to-space). One GC's survivors will be copied into the other half — that's the "copying" family.
  2. In gc_org_gc(), list the three distinct root sources scanned before any object is moved (stacks, then classes/statics, and one more). Why must the GC thread's own stack be skipped?
  3. Predict what happens to the heap after a GC when nothing is reachable: where does every object go?
