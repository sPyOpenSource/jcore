Lesson 10: The Scheduler
What runs next on a CPU

Mission: JCore is a JVM — many Java threads compete for few CPUs, and the garbage collector only works when threads are stopped at safe points. The scheduler is the ground layer the GC stands on. This lesson gives you the scheduler's job, its data structures in src/core/runq.c, and how it hands control to the collector.

The scheduler's one question

A scheduler answers a single question: given one CPU and a set of runnable threads, which one runs next? It isn't always running — it is invoked when the world changes:

EventJCore entry point
A thread becomes runnable (created)Sched_created() — runq.c:38
A thread wakes up (unblocked)Sched_unblocked() — runq.c:68
A thread voluntarily yieldsSched_yielded() — runq.c:77
A thread blocks or diesSched_blocked() / Sched_destroyed()
The timer fires (preemption)Sched_reschedule() — runq.c:137

The central invariant: a runqueue holds only STATE_RUNNABLE threads (src/Headers/core/thread.h:20). Blocking moves you out; unblocking moves you back in. Every schedule decision is "dequeue a runnable thread, switch to it."

Two-level round-robin

JCore's runqueue is not one flat queue. It is two nested queues (runq.c:25):

domain_runqueue            global: runnable domains, FIFO
   └── domain->firstThreadInRunQueue   per-domain: runnable threads, FIFO

Why two levels? Domains are the scheduling units of isolation. Round-robin between domains guarantees a runnable domain can't starve forever — even if another domain spawns 1000 threads. Then round-robin within a domain picks a thread fairly. The pick in runqueue_removeFirstOrNULL() (runq.c:301):

  1. Dequeue the head domain from domain_runqueue.
  2. If none: take the head thread from the current domain's thread runqueue.
  3. Else: append the current domain to the domain runqueue (if it still has runnable threads), then take the head thread of the dequeued domain.

Notice the scheduler itself never touches malloc — queued-ness lives in the domain's own queued flag and nextInRunQueue links, exactly like the bitmap/bump allocators you already studied.

The switch: raw context swap

Choosing is half the job; the other half is actually swapping the CPU onto the next thread. That's assembly, in src/Assembly/switch.S:

internal_switch_to:                 // save current, then restore next
    movl  %eax, PCB_EIP(%ecx)       // where we'll resume from
    movl  %esp, PCB_ESP(%ecx)       // stack pointer
    movl  %ebp, PCB_EBP(%ecx)       // frame pointer
    movl  %esi, PCB_ESI(%ecx)       // callee-saved regs
    movl  %edi, PCB_EDI(%ecx)
    ...                             // then load next thread's PCB and ret

The trick that makes it work: each thread's register state lives in its context[] PCB. Saving a thread = copying registers there; resuming = restoring them and ret into the stored EIP. The thread wakes up mid-instruction, as if the switch never happened. There's also destroy_switch_to — used when the current thread is dying, so its state is never saved.

What happens when there's nothing to run

An idle thread owns the CPU (runq.c:196):

for (;;) {
    asm("sti"); asm("hlt"); asm("cli");   // halt until interrupt
    while (domain_runqueue.first == NULL); // then wait for work
    threadyield();
}

hlt parks the CPU and consumes zero power until the next interrupt (timer, device, IPI) wakes it to re-check.

Where the GC meets the scheduler

The scheduler isn't just adjacent to GC — it cooperates with it:

  1. Roots: the scheduler holds references (to runnable threads, scheduler objects). The collector must know them. In sched_global_rr.c:472, Sched_gc_rootSet() lets the GC walk the scheduler's special root objects.
  2. Moving: in JCore's Java-scheduler mode, the scheduler itself is a Java object living in the heap. A copying GC must relocate it — see gc_org_moveSchedulerObject() at gc_org.c:48, which rewrites the scheduler reference after the copy.
  3. Safepoints: a GC must stop all mutator threads. Only a scheduler can do that — and the collector skips threads whose state marks them not-running (STATE_AVAILABLE, as in gc_org.c:1164).

So: garbage collection cannot even start without the scheduler. When we study safepoints later, this is the seam you'll revisit.

Check yourself

1. A runqueue in JCore holds which threads?

The invariant is enforced everywhere: ASSERT(thread->state == STATE_RUNNABLE) before a switch. Blocking removes a thread; unblocking re-adds it.

2. When a thread calls Sched_block(), what happens to it?

The thread's state is set to the blocking reason (e.g. STATE_BLOCKEDUSER) and it is removed from the runqueue until some event calls Sched_unblock().

3. What does the global domain runqueue guarantee?

Domains are round-robined as units, so a domain with many threads still gets only its fair turn of CPU — fairness is between domains first, threads second.

4. Why does the GC need the scheduler's help?

A GC must freeze mutators (safepoints) and know the scheduler's own references — Sched_gc_rootSet() exposes those, and gc_org_moveSchedulerObject() relocates the scheduler's Java object.

Try it yourself

  1. Trace one switch_to by hand in src/Assembly/switch.S: find where the current EIP is saved and where the next thread's EIP is loaded. Why must EIP be saved on the stack of the calling thread?
  2. In runq.c, find the two queue structures and list every place a domain gets added to domain_runqueue. What condition must hold first?
  3. Read gc_org_moveSchedulerObject() (gc_org.c:48) — it walks domain->Scheduler[i] for every CPU. Why would a copying GC need to rewrite this pointer specially, rather than finding it through a normal object graph walk?
