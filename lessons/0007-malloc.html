Lesson 7: Kernel Memory Allocator
How jxmalloc works inside JCore

Mission: Every kernel subsystem (threads, domains, portals, file systems) allocates kernel memory via jxmalloc. Understanding it means understanding how JCore manages its own memory — and why you can't just call libc malloc.

Overview

JCore's kernel memory allocator lives in src/malloc.c. It's a bitmap-based block allocator with fixed-size blocks of 1024 bytes (BLOCKSIZE in src/Headers/malloc.h:16).

Three key differences from user-space malloc:

  1. No libc — JCore has no standard library; jxmalloc is the kernel's own allocator
  2. Fixed blocks — all allocations are multiples of 1024 bytes (no variable-size chunks)
  3. Memory-type tracking — each allocation is tagged with what it's used for (heap, stack, code, etc.)

Initialization: Where does the memory come from?

jxmalloc_init() at malloc.c:85 determines the allocable memory range by reading the Multiboot2 info structure:

jxmem_end = top_of_RAM;  // 1 MB + upper_memory_size from Multiboot2 tag type 2
jxmem_start = last_boot_module_end;  // aligned to next BLOCKSIZE

So the allocator manages all RAM between the end of the last boot module and the top of physical memory. In the QEMU default (~128 MB), this is roughly 128 MB of managed memory.

The bitmap itself lives at the start of that range (bitmap = jxmem_start), eating the first few blocks.

The bitmap needs n_blocks / 8 bytes. For 128 MB with 1024-byte blocks, that's 128 * 1024 / 8 = 16 KB.

Allocation Algorithm

jxmalloc_internal() at malloc.c:384 implements a first-fit with rotating pointer:

  1. Round requested size up to next block boundary (ALIGN_NEXT_BLOCK)
  2. Convert to block count: size_blk = size >> 10
  3. Scan the bitmap for size_blk consecutive free blocks starting from current_block
  4. If alignment is needed (e.g., for thread stacks), skip blocks that don't satisfy it
  5. Mark them used, advance current_block past the allocation, return address
  6. If not found, wrap around to block 0 and scan again
  7. If still not found: sys_panic("Out of memory")

Free: jxfree()

jxfree(addr, size) at malloc.c:494 converts addr to a block number, calculates how many blocks size occupies, and clears the corresponding bits in the bitmap.

Caveat: You must pass the exact same size to jxfree that you passed to jxmalloc. The allocator cannot determine the allocation size from the address!

Two-Level Allocation

JCore has a two-tier allocation system:

Tier 1: jxmalloc (global, coarse-grained)

  • Fixed 1024-byte blocks from the global pool
  • Used for: thread stacks, code segments, DCB, large temporary allocations

Tier 2: malloc_code (per-domain, fine-grained)

malloc_code(domain, size) at malloc.c:601 is a bump allocator on top of jxmalloc:

  • Each domain has its own code segment (pre-allocated via jxmalloc)
  • Allocations are served sequentially within that segment (linear bump)
  • When a segment runs out, a new one is allocated (up to CODE_FRAGMENTS)
  • Used for: class descriptors, method descriptors, vtables, JIT-compiled code
  • No free — code memory is freed per-domain when the domain terminates

This two-tier design means the coarse-grained bitmap allocator rarely fragments, while the fine-grained bump allocator is extremely fast.

Memory Type Tracking

Every jxmalloc call includes a MEMTYPE_* tag:

void *p = jxmalloc(256 MEMTYPE_CODE);
void *q = jxmalloc(4096 MEMTYPE_STACK);
void *r = jxmalloc(64 MEMTYPE_HEAP);

These tags are used for statistics (printed by jxmalloc_stat()) to track how kernel memory is distributed.

Thread Stacks

malloc_threadstack() at malloc.c:868 allocates stack memory with alignment support (important for stacks that need %esp alignment to a page boundary).
