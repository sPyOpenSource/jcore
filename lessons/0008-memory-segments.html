Lesson 8: Memory Segments

.bss, .data, Stack, and Heap — where does your data actually live?

Why This Matters Right Now

You are debugging a crash where JCore's zip pointer (0x2629f4) is silently zeroed. It lives in .bss. Your java_lang_Object pointer (0x261968) lives there too — and it's also zeroed at the crash site. Between them sits emergency_stack[1024] and the jxmalloc bitmap statics. Understanding what each memory segment is, and why it behaves differently, is the key to fixing this.

This lesson maps each segment onto your actual linker.ld and your running kernel, so you can see exactly where your data lives — and why .bss corruption is so destructive.

1. The Four Memory Territories

Every process (and every kernel) divides its address space into four logical regions. They differ in initial value, lifetime, and allocation mechanism:

SegmentInitial valueGrowsManaged byTypical contents
.dataexplicit initfixedlinkerglobal variables with non-zero init
.bsszerofixedlinker + loaderglobal variables with zero/no init
StackundefineddownwardCPU (push/pop)local vars, return addresses, call frames
Heapundefinedupwardmalloc/freedynamically allocated data
Key insight: .data and .bss are fixed-size regions carved out at link time. The stack and heap are dynamic — they grow into adjacent free memory. If they collide, you corrupt data.

2. .data — The Initialized Data Segment

This is where global variables with non-zero initial values live. The linker copies the initial values straight from the ELF file into RAM when the kernel is loaded.

In linker.ld (line 21–23):

.data : {
    *(.data)
}
edata = .;

Examples in JCore:

// in serialdbg.c — initialized, so it goes in .data
static int ser_io_base[] = { 0x3f8, 0x2f8, 0x3e8, 0x2e8 };

These values survive even if something zeroes .bss — they live in a different address range. That's why ser_putchar still works after the corruption: ser_io_base[] is safe in .data.

3. .bss — The Zero-Initialized Data Segment

Global variables that are uninitialized or explicitly zeroed go here. The ELF file doesn't store zero bytes on disk — it just records the address range in a program header of type NOBITS. The bootloader (or startup code) zeroes this range at load time.

In linker.ld (line 26–29):

.bss : {
    *(.bss)
    *(COMMON)
}
end = .;

JCore examples:

// in load.c — no initializer → goes to .bss
ClassDesc *java_lang_Object;          // 0x261968
Class *java_lang_Object_class;        // 0x26196c

// in zip.c — no initializer → .bss
static char *zip;                     // 0x2629f4

// in malloc.c — all go to .bss
static char *jxmem_start;             // 0x2629cc
static char *jxmem_end;               // 0x2629d0
static u4_t n_blocks;                 // 0x2629d4
static u1_t *bitmap;                  // 0x2629e0
The debugging connection: When .bss gets zeroed at runtime, every global pointer stored in this range becomes NULL at once:
  • zip = NULL → zip_next_entry PANICs
  • java_lang_Object = NULL → class hierarchy breaks
  • jxmem_start = 0 → jxmalloc starts allocating from address 0
This is why a single corruption crashes everything at once.

Who clears .bss?

In your kernel, crt0.S lines 38–43 comment out the .bss clear:

# lea  edata, %edi
# lea  end, %ecx
# sub  %ecx, %edi
# xor  %eax, %eax
# rep  stosb           ; ← this would zero from edata to end

In theory, GRUB reads the ELF program headers and zeroes .bss-type segments before jumping to your kernel. In practice, whether GRUB does this depends on: (a) whether the ELF program headers include a segment covering .bss, and (b) whether GRUB respects it under Multiboot2.

4. Stack — The Automatic Memory

The stack is a LIFO structure. The ESP/RSP register points to the top. PUSH decrements ESP and writes; POP reads and increments.

In JCore, the initial stack is set up in crt0.S (line 35):

movl $base_stack_end, %esp

And stack.S defines the buffer:

.globl base_stack_start
base_stack_start:
    .space 32768       ; 32 KB boot stack
base_stack_end:

Your linker script places this at 0x250000–0x258000. The stack grows downward from 0x258000: the first function call pushes to 0x257FFC, then 0x257FF8, etc.

PropertyValue in JCore
Base address0x250000 (base_stack_start)
Initial ESP0x258000 (base_stack_end)
Size32 KB (32768 bytes)
Growsdownward (toward lower addresses)

Stack frame layout (cdecl calling convention)

Higher addresses (0x258000)
  ┌──────────────────────┐
  │   local variables    │ ← EBP - 8, EBP - 4, etc.
  ├──────────────────────┤
  │   saved EBP          │ ← EBP points here (old frame pointer)
  ├──────────────────────┤
  │   return address     │ ← EBP + 4 (return EIP)
  ├──────────────────────┤
  │   function arguments │ ← EBP + 8, EBP + 12, etc.
  ├──────────────────────┤
  │   ... next frame ... │
  Lower addresses (0x250000)
Your debugging clue: You see ESP: 0x00257ec8 on early malloc_code calls. That's 0x258000 - 0x17EC8 = 312 bytes from the top — still in the boot stack. After threads_init(), you see ESP: 0x00. If the actual ESP register is really 0, the CPU is using the top of the 4 GB address space (0xFFFFFFFC) for its stack — a sure sign that something loaded a zeroed PCB_ESP from a corrupt thread context.

5. Heap — The Dynamic Memory

JCore has two heap allocators:

5a. jxmalloc — The Kernel Bitmap Allocator

Covers the physical memory range not used by the kernel or boot modules. It uses a simple bitmap in RAM:

// malloc.c:55-61
static char *jxmem_start;   // start of managed memory
static char *jxmem_end;     // end of managed memory
static u4_t n_blocks;       // total 1024-byte blocks
static u1_t *bitmap;        // 1 bit per block (1 = used, 0 = free)

Initialized in jxmalloc_init() (malloc.c:85): sets jxmem_start after the last boot module, jxmem_end at the top of physical RAM, divides into 1024-byte blocks, and uses the first few blocks as the bitmap itself.

Your debug output shows jxmem_start ≈ 0x0744ac00 (~121 MB) and jxmem_end ≈ 0xb8d88000 (~3 GB), giving about 2 MB of managed blocks.

5b. Domain Code Allocator (bump allocator)

Each domain (including DomainZero) has a fast bump allocator for code memory (malloc_code). It allocates from fixed-size chunks allocated via jxmalloc. The bump pointer just advances — no free, no reuse.

// malloc.c:602-639
char *malloc_code(DomainDesc *domain, u4_t size) {
    if (domain->cur_code == -1) {
        domain->code[0] = jxmalloc(chunksize MEMTYPE_CODE);
        // ... allocate first chunk from jxmalloc
    }
    data = domain->codeTop[c];   // bump pointer
    domain->codeTop[c] += size;  // advance
    return data;
}

7. The Bug in Context

Here's how the segments interact in your crash:

  1. .bss gets zeroed — something writes zeros across 0x261930–0x26924c. All your globals (zip, java_lang_Object, jxmem_start, etc.) become NULL.
  2. jxmalloc breaks — jxmem_start = 0 makes the bitmap allocator think memory starts at address 0. Subsequent jxmalloc calls return addresses near 0.
  3. Thread stacks get corrupted — malloc_threadstack uses jxmalloc_align, which now returns addresses near 0. The DomainZero thread's stack pointer PCB_ESP becomes a small number near 0.
  4. ESP = 0 — the thread switch loads the corrupted PCB_ESP. The CPU tries to use the stack at address 0, wrapping to 0xFFFFFFFC on first push.
  5. zip == NULL — zip_reset in read_codefile reads from address 0, passing garbage to the ZIP parser, which panics with "wrong central header signature".

Any one of these symptoms is a consequence of the same root cause: something writing zeroes to .bss at runtime.

8. Why This Debugging Technique Works

The ESP-printing you added to malloc_code is a great diagnostic for exactly this reason: it tells you when your actual runtime stack has diverged from the boot stack. Normal ESP values are around 0x00257ec8 (boot stack). If you see 0x00 or very small values, you know a thread context was loaded from corrupted memory.

To isolate .bss corruption specifically, a GDB watchpoint on 0x2629f4 (zip) would catch the write. But as you found, OVMF boots in 64-bit mode and GDB connection fails. Alternative: insert prints before/after every suspected write, or binary-search which function zeroes the range.
