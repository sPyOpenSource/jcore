ARMv7-A RTOS Context Switching

SysTick, PendSV, and the deferred switch pattern

The Core Idea

A preemptive RTOS lets the CPU switch between tasks at fixed time intervals, without the task having to yield. Each task gets a slice of CPU time. The switch happens in an exception handler — either SysTick directly, or PendSV deferred.

Two Stack Pointers

ARMv7-A has two stack pointers, and this is the foundation of clean context switching:

PointerUsed inStores
MSP (Main Stack Pointer)Handler mode (exceptions)Kernel's stack — scheduler state, SVC handler locals
PSP (Process Stack Pointer)Thread mode (task code)Task's stack — local variables, saved registers

When an exception fires, the hardware automatically uses MSP for the handler. The interrupted task's stack pointer remains in PSP. This means the exception handler can save and restore PSP without ever touching the task's stack from the kernel's side.

SysTick → PendSV → Switch

The standard RTOS pattern uses three exceptions working together:

Timer tick (e.g., 1 ms):
  ┌──────────┐
  │ SysTick  │  Fires on timer. Increments tick count.
  │          │  Pends PendSV via ICSR[28] = 1.
  └────┬─────┘
       │ return from exception
       ▼
  ┌──────────┐
  │  Task    │  Continues running briefly (or PendSV fires immediately
  │  code    │  if no other IRQs are pending).
  └────┬─────┘
       │ PendSV fires (lowest-priority exception)
       ▼
  ┌──────────┐
  │ PendSV   │  Saves r4–r11 of current task.
  │ Handler  │  Calls scheduler_next().
  │          │  Restores r4–r11 of next task.
  └────┬─────┘
       │ return from exception
       ▼
  ┌──────────┐
  │ Task N+1 │  Next task runs.
  └──────────┘
Why defer to PendSV? If you context-switch inside SysTick, the ISR is running on MSP. Any registers saved on the stack are mixed with the exception frame. PendSV runs at the lowest priority — it waits until all other IRQs are done, so you never preempt an ISR with a context switch.

What the Hardware Saves Automatically

On exception entry, ARMv7-A pushes eight registers onto the current stack (for PendSV, that's PSP since tasks run in thread mode):

[PSP-0x20]  r0
[PSP-0x1C]  r1
[PSP-0x18]  r2
[PSP-0x14]  r3
[PSP-0x10]  r12
[PSP-0x0C]  LR (return address to interrupted code)
[PSP-0x08]  PC (address of next instruction)
[PSP-0x04]  xPSR (program status)
[PSP]       ← SP now points here

This is the exception frame. On exception return (BX LR with EXC_RETURN), the hardware pops these and resumes execution.

What the PendSV Handler Saves

The PendSV handler only needs to save callee-saved registers (r4–r11) because the compiler guarantees they're preserved across function calls. Everything else (r0–r3, r12, LR, PC, xPSR) is already on the stack from the hardware exception frame.

PendSV_Handler:
    mrs     r0, psp              ; r0 = task's PSP
    stmdb   r0!, {r4-r11}        ; push r4–r11 onto task stack

    ; Now r0 = new task SP (after pushing 8 × 4 = 32 bytes)
    ldr     r1, =current_tcb
    str     r0, [r1]             ; TCB.sp = current SP

    ; Pick next task
    bl      scheduler_next       ; r0 = &next_TCB

    ; Load next task's saved SP
    ldr     r0, [r0]             ; r0 = next TCB's sp
    ldmia   r0!, {r4-r11}        ; pop r4–r11
    msr     psp, r0              ; restore PSP

    bx      lr                   ; EXC_RETURN in LR → pop exception frame

Total save/restore per context switch: 8 registers × 4 bytes × 2 directions = 64 bytes of stack traffic. The other 8 registers (r0–r3, r12, LR, PC, xPSR) are handled by hardware.

Now: The Domain Question

From the grilling session, you said the SVC table should live in domain 0 (MANAGER) so task-domain reads of it fault. Let's trace through what actually happens:

  1. Task runs in thread mode (SVC mode, but using PSP). DACR domain 0 = MANAGER, domain 1 = CLIENT. Task memory is in domain 1.
  2. Task executes SVC 0. Hardware switches to handler mode (still SVC mode, but now using MSP).
  3. SVC handler runs. It needs to read the SVC table. The SVC table's page table entry has domain = 0.
  4. The access check: The MMU checks the page table entry's domain field against DACR. Since DACR[0] = MANAGER (doesn't check permissions), the read succeeds.

But here's the subtlety: the handler runs in the same domain configuration as the task. Entering SVC mode does NOT change DACR. If DACR[0] were CLIENT instead of MANAGER, the SVC handler would fault when reading its own table — because the page table entry says domain 0, and the CPU checks DACR[0] regardless of which mode it's in.

The common mistake: People assume "handler mode" or "SVC mode" implies kernel privileges. For the MMU, privilege comes from page table permission bits (AP bits), not from the mode. For domains, it's purely about the DACR value, which is the same in all modes unless you explicitly change it.

Nailing It Down

The correct design is:

RegionDomainDACR settingWho can access
SVC table0MANAGER (0b11)Any mode (no permission checks)
Kernel .text/.data0MANAGERAny mode
Task 0 stack + TCB1CLIENT (0b01)Only via page table AP bits (SVC only, typically)
Task 1 stack + TCB2CLIENTSame — SVC-only access
UART / GPIO (device)3CLIENTAP bits set for SVC-only or SVC+user

If you set SVC table to MANAGER (domain 0), any code running at any privilege level can read it — including a buggy task. MANAGER bypasses all permission checks including AP bits. To truly protect the table from tasks, you'd need domain 0 as CLIENT and tasks as a different CLIENT domain, with the table's AP bits set to SVC-only (AP[1:0] = 0b11).

But — in your RTOS (no user mode, everything in SVC mode), the AP bits don't help. Everything is SVC privileged. So the real protection is not running user mode at all, and accepting that a buggy task can crash the kernel. Domains protect memory regions from each other (task A's stack from task B), not tasks from the kernel.

Quiz: Check Your Understanding

Answer each in one sentence before looking at the answer.

Q1: Why does the PendSV handler use PSP instead of MSP?

Answer: Because the interrupted task's registers are on its own stack (PSP), not the kernel's stack (MSP). Using MSP would save kernel-internal data, not task state.

Q2: What would happen if you context-switched inside the SysTick handler directly (no PendSV)?

Answer: The context switch would happen on MSP, possibly while a higher-priority IRQ was still being processed, leading to stack corruption or races between the scheduler and interrupt handlers.

Q3: Does setting a domain to MANAGER make it more or less restricted?

Answer: Less restricted — MANAGER bypasses all permission checks. CLIENT enables them. This is counterintuitive: MANAGER means "I manage this, don't check permissions."
